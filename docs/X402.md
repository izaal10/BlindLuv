# x402 on Monad

[x402](https://x402.org) revives `HTTP 402 Payment Required`: a server answers
402 with machine-readable payment requirements, the client pays, and retries the
same request with an `X-PAYMENT` header. No accounts, no API keys, no invoices.

BlindLuv uses it twice — once to unlock a match, once for the concierge.

---

## Why the SDK could not be used

The published `x402` package (v1.2.0) hard-codes a network enum:

```
"base", "base-sepolia", "avalanche", "avalanche-fuji", "iotex",
"polygon", "polygon-amoy", "sei", "sei-testnet", "solana", "solana-devnet", …
```

No Monad. So the SDK is unusable here regardless of what the chain supports.

The protocol itself, though, only needs the asset to implement **EIP-3009**
(`transferWithAuthorization`) — and Monad testnet USDC does. Probed directly:

```
name()      → "USDC"
version()   → "2"
decimals()  → 6
TRANSFER_WITH_AUTHORIZATION_TYPEHASH() → 0x7c7c6cdb…
transferWithAuthorization(…,uint8,bytes32,bytes32) → reverts "FiatTokenV2: invalid signature"
transferWithAuthorization(…,bytes)                 → reverts "ECRecover: invalid signature length"
```

Both overloads reverting on *signature validation* proves they exist and are
reachable — it is `FiatTokenV2_2`. So `web/src/lib/x402/` implements the v1 wire
format by hand, and the facilitator is self-hosted. An x402 release that adds
`monad-testnet` should be drop-in compatible with what this server emits.

## The flow

```
client                          BlindLuv                       facilitator        Monad
  │  POST /api/reveal              │                                │              │
  ├───────────────────────────────►│                                │              │
  │  402 + accepts[]               │                                │              │
  │◄───────────────────────────────┤                                │              │
  │                                │                                │              │
  │  sign EIP-3009 (no gas!)       │                                │              │
  │                                │                                │              │
  │  POST + X-PAYMENT              │                                │              │
  ├───────────────────────────────►│  verify ──────────────────────►│  eth_call ──►│
  │                                │◄─────────────────────── isValid │              │
  │                                │  ── produce the resource ──     │              │
  │                                │  settle ──────────────────────►│  broadcast ─►│
  │  200 + X-PAYMENT-RESPONSE      │                                │              │
  │◄───────────────────────────────┤                                │              │
```

**Order matters.** Verify is cheap and involves no broadcast, so it runs first.
Settlement runs *after* the resource is produced — otherwise a failed reveal
would still charge the user.

The payer signs a message, not a transaction. The facilitator pays the gas, so
**a user needs USDC and no MON at all** — that is the property that makes x402
worth more than a plain on-chain transfer.

## What verification actually checks

A facilitator that only checks the signature is a facilitator that settles
bounced payments. `verify()` requires all six:

| Check | Failure reason |
| --- | --- |
| Network matches the requirements | `network_mismatch` |
| Recipient matches `payTo` | `recipient_mismatch` |
| Value ≥ `maxAmountRequired` | `insufficient_amount` |
| `validAfter` ≤ now, and `now + 6s` < `validBefore` | `authorization_not_yet_valid` / `authorization_expired` |
| EIP-712 signature valid for `from` | `invalid_signature` |
| Nonce unused **and** balance sufficient (on-chain) | `authorization_already_used` / `insufficient_funds` |

The six-second headroom on expiry exists so the authorization is still valid
when the settle transaction lands. Monad finalises in ~800ms, so it is generous.

### Verified against live Monad testnet

`web/scripts/x402-probe.mjs` signs real EIP-3009 authorizations with a throwaway
key and puts them through the running facilitator:

```
verify (valid signature, empty wallet) → { isValid: false, invalidReason: 'insufficient_funds' }
verify (tampered amount)               → { isValid: false, invalidReason: 'insufficient_amount' }
verify (expired window)                → { isValid: false, invalidReason: 'authorization_expired' }
```

`insufficient_funds` is the good result: the signature verified, the RPC was
reached, and only the real on-chain balance check failed.

## EIP-7702 and smart-account payers

USDC validates authorizations through Circle's `SignatureChecker`, which
branches on whether the payer has code:

```
payer has no code  → ECDSA.recover(digest, signature) == payer
payer has code     → payer.isValidSignature(digest, signature)   (EIP-1271)
```

An **EIP-7702-delegated EOA has code**, so it takes the second branch. If its
delegate does not implement EIP-1271 correctly, the transfer reverts with
`FiatTokenV2: invalid signature` — even though the ECDSA signature is
perfectly valid, which makes it a genuinely confusing failure.

Observed on real Monad testnet, on the well-known Anvil test accounts (their
keys are public, so anyone can delegate them):

```
$ cast code 0x70997970C51812dc3A010C7d01b50e0d17dc79C8 --rpc-url https://testnet-rpc.monad.xyz
0xef01006bd9b71559e3b2013596726a4e2ca1ee97189606
```

`verify()` therefore checks for code on the payer and returns
`payer_has_eip7702_delegation` / `payer_is_contract_wallet` up front, rather
than letting the user discover it as a revert after the resource was produced.

A smart account that *does* implement EIP-1271 properly will work — the check
is conservative, and loosening it is a matter of attempting the 1271 call
during verification.

## Settlement failure withholds the payload

Verification runs before the resource is produced and settlement after it. So a
payment that verifies but fails to broadcast — a 1271 wallet that rejects it, a
relayer out of gas, a nonce raced by a concurrent request — would otherwise
return the identity for free.

`settleAndRespond` returns `402` and drops the payload when
`receipt.success` is false. The work already done is wasted, which is the
cheaper of the two mistakes: the alternative breaks the one rule the product
rests on.

## The two-gate rule

`/api/reveal` is the only endpoint that discloses identity, and it requires
**both**:

1. x402 payment settled, and
2. `isUnlocked(sessionId) == true` on Monad — meaning *both* participants staked.

Paying alone reveals nothing. Without the second gate, one person could buy
their way to another person's contact details, which would defeat the entire
premise.

`/api/concierge` is x402-gated but has no on-chain gate, because it discloses
nothing identifying — only venue types.

## Endpoints

Standard facilitator surface, exposed publicly so any x402 client can use it:

| Endpoint | Purpose |
| --- | --- |
| `GET /api/x402/facilitator/supported` | advertised schemes + whether settlement is available |
| `POST /api/x402/facilitator/verify` | the six checks above; no key required |
| `POST /api/x402/facilitator/settle` | broadcasts `transferWithAuthorization` |

### Example 402 response

```json
{
  "x402Version": 1,
  "error": "X-PAYMENT header is required",
  "accepts": [{
    "scheme": "exact",

    "resource": "https://your-app.vercel.app/api/reveal",

    "mimeType": "application/json",
```

## Client side

`web/src/lib/x402/client.ts` handles the challenge transparently:
request → 402 → sign → retry. It takes an `onChallenge` callback so the UI can
show the price and get consent **before** prompting the wallet — an unexplained
signature prompt is how people lose money.
